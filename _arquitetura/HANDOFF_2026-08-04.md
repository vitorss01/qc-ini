## 2. O que existe hoje

### Arquitetura

```
Origem → Power Query → STG_Importacao → validação → atribuição de RUN
   → mDados.Upsert → DB_Resultados → mEstatistica → Eng_Saida → interface
```

- **`DB_Resultados`** é a única fonte operacional. Só `mDados` grava nele.
- **`mEstatistica`** é a única camada que calcula. Publica em `Eng_Saida`.
- **`Painel`, `Estatística`, `Calc`** apenas consomem, por fórmula.
- **`Audit_Log`** é o Event Store: append-only, encadeado por SHA-256.
- **`LOG_Resultados` / `LOG_Registros`** (dentro do `DB_Resultados`, colunas
  `BG..BY` e `CB..CT`) são a estrutura física por origem, ligadas ao Event Store
  pelo `ID_Auditoria`.

### Entregue nesta sessão

| Item | Situação |
|---|---|
| Trilha de auditoria com 33 colunas, tabela filtrável | ✅ + aba `Audit_Legenda` |
| Detecção de adulteração do log | ✅ aponta a linha exata |

## 4. Suspeitas e riscos — leia antes de mexer

### 4.1 Alta — a propagação vai expor suposições sobre `NLV`

Aposto que a primeira tentativa de rodar o pipeline sobre Bioquímica quebra em
algum ponto onde o `3` está escrito em vez de lido. Já mapeei três lugares
(`mEstatistica.NLV`, `criar_eng_saida.ps1`, blocos do `Calc`), e **provavelmente
há mais**.

**Recomendação:** antes de propagar, rodar uma varredura procurando `3` literal
nos scripts e módulos e listar cada ocorrência. É trabalho chato e evita um dia
inteiro de depuração.

### 4.2 Alta — `build_all.ps1` está amarrado a Hematologia

Nome do arquivo, caminho do snapshot, nome da pasta de build. Propagar exige
parametrizar por produto. **Sugestão:** `build_all.ps1 -Produto Bioquimica`, com
os caminhos derivados do nome, e o `snapshot_producao/<Produto>/` já segue essa
convenção.

### 4.3 Média — a aba `Registros` ainda aceita digitação

A Sprint NC alimenta a aba pelo formulário, mas **não bloqueei a digitação
manual**. Isso depende de incluir `Registros` na blindagem com proteção
persistida. Enquanto não for feito, alguém pode digitar uma ocorrência que não
corresponde a nenhuma linha do banco — exatamente a classe de erro que a sprint
queria eliminar.

### 4.4 Média — o marcador do gráfico mudou de significado, o rótulo não

A coluna `F` da `Registros` era "Rep 1" e agora recebe o resultado não conforme.
O gráfico plota o mesmo marcador, mas o cabeçalho e a legenda ainda dizem
"repetição". Não é defeito funcional; é rótulo enganoso, e num sistema de
qualidade isso importa.

### 4.5 Média — item 2.2 provavelmente já está satisfeito, mas não foi verificado

O `Audit_Log` guarda `ResultadoAnterior`, `ResultadoNovo`, `Delta` e
`SeqAlteracao` como **dados**. Recuperar o valor original de qualquer resultado é
filtrar `ChaveRegistro` e olhar `Seq = 1`. Falta um teste que faça exatamente
isso e feche o item. **Não marquei como fechado sem teste** — foi o erro que
custou caro no item 2.1.

### 4.6 Baixa — verificação da cadeia é O(n)

`VerificarIntegridadeLog` recalcula todos os hashes desde o gênese. Com 59
eventos leva 0,31 s. Com dezenas de milhares, depois de anos de uso, pode
incomodar. Não é problema hoje; é bom saber que existe. A saída natural, se um
dia doer, é verificação incremental com pontos de controle assinados.

### 4.7 Baixa — repositório e `.git` dentro do OneDrive

Repositório Git em pasta sincronizada é fonte conhecida de corrupção de índice
quando duas máquinas sincronizam — e você trabalha em casa e no serviço. Não deu
problema até agora, mas o risco é real. Mover o repositório para fora do OneDrive
elimina a variável.

## 5. Armadilhas já pagas — não repita

Todos os erros caros desta sessão foram de **fronteira entre ferramentas**,
nenhum de lógica de CQI. A matemática (Westgard, Sigma, elegibilidade, erro
total) não deu um problema sequer desde que foi validada contra o Python.

| Armadilha | Sintoma enganoso |
|---|---|
| `aS` é a palavra reservada `As` (VBA é insensível a maiúsculas) | erro em rotina de outro módulo |
| Dois procedimentos `Public` com o mesmo nome | "nome ambíguo", derruba o projeto todo |
| `Select-Object -First` **encerra o script produtor** | etapa morre antes do `Save`, reportando sucesso |
| Referências COM presas no runspace | arquivo travado, aberto em somente leitura **sem aviso** |
| Matar o Excel repetidamente | desestabiliza DCOM: `0x80080005`, nem o `excel.exe` abre |
| `AutomationSecurity = 3` | é *ForceDisable* — desabilita as macros |
| Hash sobre valor pretendido, não gravado | falso positivo de adulteração |
| `ListObject` nasce com linha de dado em branco | primeiro evento cai na linha errada |
| `powershell.exe -File` não interpreta vírgula em array | Excel procura macro chamada `"a,b,c"` |
| `"$var:"` em string do PowerShell | lido como variável qualificada por unidade |

**Regra que emergiu de tudo isso:** rodar o analisador de sintaxe do PowerShell
em todo script alterado, **antes** de executar. Custa segundos e evitou pelo
menos quatro ciclos de build perdidos.

```powershell
$e = $null
[void][System.Management.Automation.Language.Parser]::ParseFile((Resolve-Path x.ps1), [ref]$null, [ref]$e)
if ($e.Count) { $e[0].Message }
```

## 6. Princípios que não devem ser quebrados

1. **Nada entra na `main` enquanto o gate tiver ⏳ ou ❌.**
2. **A produção não é tocada.** Todo trabalho acontece em cópia de build.
3. **Conferir, não confiar.** O pipeline reportava intenção, não resultado — foi
   assim que o motor corrigido ficou fora do `.xlsm` por semanas em duas
   máquinas. Toda etapa agora verifica o que fez.
4. **Nenhum item do gate fecha sem teste executado.** Leitura de código não
   conta.
5. **Estado escrito em código é proibido.** Elegibilidade e tipos de NC vêm da
   `Cfg_Status`; acrescentar um estado é digitar uma linha.
6. **O hash cobre o valor gravado**, nunca o pretendido.
